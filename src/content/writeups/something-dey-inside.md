## 1. Reconnaissance du fichier

```bash
file memdump.core
# memdump.core: ELF 64-bit LSB core file, x86-64, ... from '/work/target'
```

> **C'est quoi un *core dump* ?**
> Quand un programme plante (segfault) ou qu'on le force, le noyau Linux peut écrire une **photographie complète de sa mémoire** à cet instant précis : la pile (stack), le tas (heap), les registres du CPU, les bibliothèques chargées… Tout est figé dans un fichier ELF de type `core`. En forensics, c'est une mine d'or : tout ce que le programme manipulait en RAM (mots de passe, clés, buffers déchiffrés…) est potentiellement dedans. Ici le binaire d'origine s'appelait `/work/target`.

Premier réflexe — chercher le flag en clair :

```bash
strings memdump.core | grep -iE 'brctf|flag|br\{'
# (rien)
```

Si le flag était en texte brut, `strings` l'aurait sorti directement. L'absence de résultat indique que le flag est **transformé** (encodé, chiffré ou obfusqué).

---

## 2. Ouvrir le core dans GDB

```bash
gdb -c memdump.core -q
```

```
Core was generated by `/work/target'.
#0  0x00007f7a27fed503 in ?? ()
(gdb) info registers
rax   0xfffffffffffffdfc   -516
...
r13   0x7ffc56ad1498
r14   0x55c1a6496dd8
rsp   0x7ffc56ad12f8
```

- `rax = -516` → code `-ERESTART_RESTARTBLOCK`. Le process était en plein appel système bloquant (probablement un `read()` en attente) au moment du dump.
- `rsp` = sommet de la pile : c'est là que vivent les variables locales, buffers temporaires et secrets déchiffrés.
- Les adresses `0x7ffc...` sont la stack, `0x55c1...` le binaire/heap, `0x7f7a...` les bibliothèques partagées (libc, ld).

### Cartographie mémoire

```
(gdb) info proc mappings
0x55c1a6493000 ... /work/target      <- segments du binaire (présents !)
0x7f7a27f1e000 ... libc.so.6
0x7f7a28105000 ... ld-linux-x86-64.so.2
```

Le binaire `/work/target` est inclus dans le core (plage `0x55c1a649xxxx`) — il aurait pu être désassemblé depuis le dump pour comprendre l'algorithme de chiffrement, mais ce ne fut pas nécessaire ici.

## 3. Fouiller la pile — repérer l'anomalie

```
(gdb) x/40gx $rsp
```

On dumpe la pile en binaire pour l'analyser tranquillement :

```
(gdb) dump binary memory stack.bin 0x7ffc56ad12f8 0x7ffc56ad1500
```

```bash
xxd stack.bin
```

Deux choses sautent aux yeux :

```
00000030: 00f6 d789 c582 7186  ......q.    <- bloc X (commence par 0x00)
00000038: 3405 2e32 6905 6e39  4..2i.n9    <- bloc Y
00000040: 3405 2e32 6905 6e39  4..2i.n9    <- bloc Y (RÉPÉTÉ !)
```

1. Le bloc `00 f6 d7 89 c5 82 71 86` commence par `0x00` : c'est la signature d'un **stack canary**, pas le flag. On l'écarte.
2. Le bloc `34 05 2e 32 69 05 6e 39` apparaît **deux fois d'affilée**. Une donnée qui se répète dans un contexte chiffré est le point faible qu'on exploite.

> **C'est quoi un stack canary ?** Une valeur aléatoire de 8 octets que le compilateur place sur la pile pour détecter les buffer overflows ; le programme vérifie qu'elle n'a pas été écrasée avant de quitter une fonction. Son premier octet est toujours `0x00` (un null byte), exprès pour bloquer les attaques par copie de chaîne — c'est ce qui permet de le reconnaître immédiatement et de l'écarter du flag.

---

## 4. Casser le XOR

Avec une clé d'un seul octet (256 possibilités), on peut brute-forcer le bloc répété en une boucle :

```python
blk = bytes.fromhex("34052e3269056e39")
for k in range(256):
    dec = bytes(b ^ k for b in blk)
    if all(32 <= c < 127 for c in dec):   # garde seulement le lisible
        print(f"{k:#04x} -> {dec}")
```

Résultat décisif :

```
0x5a -> b'n_th3_4c'
```

`0x5a` est le caractère `'Z'`, et `n_th3_4c` est du leetspeak pour « in the act ». Ce n'est pas un hasard : toute la mémoire est XORée avec `0x5a`. Le bloc était répété parce que le programme avait recopié ce fragment du flag à deux endroits de la pile — deux copies identiques du même texte chiffré est un signal fort de données structurées, pas de bruit aléatoire.

---

## 5. Déchiffrer tout le core

Le `stack.bin` ne contenait qu'un fragment (la plage dumpée était minuscule). On applique `XOR 0x5a` au core entier :

```bash
python3 -c '
d = open("memdump.core","rb").read()
x = bytes(b ^ 0x5a for b in d)
open("dec.bin","wb").write(x)
'
strings dec.bin | grep -iE 'brctf\{|n_th3'
```

Sortie :

```
beacon_interval=60;flag=brctf{pr0c3ss_h0ll0w1ng_caught_1n_th3_4ct}
```

**Flag :** `brctf{pr0c3ss_h0ll0w1ng_caught_1n_th3_4ct}`

> Les zones mémoire non initialisées sont à `0x00`, et `0x00 ⊕ 0x5a = 0x5a = 'Z'` : les suites de `Z` visibles après déchiffrement sont simplement de la mémoire vide, ce qui confirme au passage que la clé est bien `0x5a`.

---

## 6. Comprendre le thème du challenge

Le flag et le contexte racontent une histoire :

- `beacon_interval=60` → configuration d'un **beacon C2** (un malware qui « appelle à la maison » toutes les 60 secondes).
- `process hollowing` → technique d'injection : on lance un process légitime, on vide sa mémoire et on y injecte du code malveillant. Le process a l'air normal de l'extérieur mais exécute autre chose.
- `caught in the act` → le process a été pris sur le fait, justement grâce au core dump qui a figé sa mémoire.

Le jeu de mots de l'énoncé (« this thing no dey behave normal », « something had been left behind ») décrit exactement un process hollowing : quelque chose d'injecté **à l'intérieur** d'un process qui semble normal — le titre « Something Dey Inside » était l'indice depuis le début.

## Récapitulatif de la chaîne d'exploitation

1. **`file`** → core dump ELF 64-bit.
2. **`strings | grep`** → rien en clair, le flag est chiffré.
3. **GDB** → `info registers`, `info proc mappings`, puis dump de la pile.
4. Repérage d'un **bloc répété** sur la pile (écarté : le stack canary, reconnaissable à son `0x00` initial).
5. **Brute-force XOR mono-octet** sur le bloc répété → clé `0x5a`.
6. **XOR 0x5a** appliqué au core entier → flag en clair.

> **Concept clé :** quand `strings` ne donne rien sur un dump mémoire, le secret est souvent simplement XORé avec une clé courte. Un bloc de données qui se répète dans un contexte chiffré est un point d'appui direct pour casser le chiffrement par brute-force.
